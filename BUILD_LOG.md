# ProofGate — Build Log

## 2026-11-20 — Phase 1: spec + deterministic core engine (no UI)

Built by the core-engine workstream for #BuildHybridAI 2026. The product UI is a separate later phase (brand assets are being produced in parallel); this phase delivers the spec and the tested, framework-free core that the UI will call.

### What was built

- `SPEC.md` — product spec: claim pipeline, hybrid routing policy (deterministic-only / on-device Gemini Nano / cloud Gemini escalation triggers), deterministic gate rules R1–R4, Proof Report format (`proofgate.report/1`) with SHA-256 sealing and replay, Firebase AI Logic integration design (JS SDK, hybrid inference, App Check, Firestore persistence, demo/mock mode), and the Devpost judging mapping. No Firebase project is connected yet; the spec says so explicitly.
- Core engine, TypeScript, Node, no UI, no network calls, no API keys anywhere:
  - `src/types.ts` — Claim, CheckResult, ModelOutput, ClaimVerdict, ProofReport types.
  - `src/claimSplitter.ts` — deterministic splitter (line + sentence segmentation, decimal-safe, character spans preserved).
  - `src/validators/arithmetic.ts` — recomputes explicit equations, priced line totals, and percent-of statements (tolerance 0.01).
  - `src/validators/dates.ts` — ISO / US / long-English date extraction with real-calendar validation, weekday cross-check, and cross-claim issue-date vs due-date ordering.
  - `src/validators/units.ts` — stated unit conversions (length, mass, storage, time) recomputed against a fixed table, 2% tolerance; cross-dimension conversions fail.
  - `src/validators/citations.ts` — URL well-formedness, DOI shape, missing-citation warning when a source is invoked without one.
  - `src/validators/numericConsistency.ts` — whole-document checks: subtotal + tax = total, line-item sum vs total, conflicting values for the same labelled figure.
  - `src/gate.ts` — deterministic verdict gate (R1 hard fail, R2 confident model contradiction, R3 review signals, R4 pass) and worst-wins rollup.
  - `src/report.ts` — Proof Report builder, canonical JSON, SHA-256 `inputHash` and `contentHash` via `node:crypto`, `verifyProofReport`.
  - `src/modelAdapter.ts` — `ModelAdapter` interface, pure `decideRoutingTier` routing policy, and `MockModelAdapter` (deterministic, `source: "mock"` on every output) for demo mode and tests.
  - `src/engine.ts` — `runProofGate(text, options)`: split → per-claim validators → document validators → routing + model pass → gate → sealed report.
  - `src/index.ts` — public exports.
- `tests/proofgate.test.ts` — 45 tests (Vitest): every validator (pass / fail / skip paths), date ordering, numeric consistency, gate rules including "model can never override a hard failure", routing tiers, report sealing / tamper detection / determinism, and the end-to-end invoice case below.
- `sample-proof-report.json` — a real sealed report generated by the engine from the test invoice (overall FAIL, 5 claims, 1 fail, contentHash `db5ccba427cb053320569cffd957c0c537fa6292978381c486d0bb1a21959748`), generated by `make-sample.mjs` against the compiled build.

### End-to-end case (in the test suite)

Input invoice contains one planted arithmetic error: `Design services: 3 units at $2,800 = $9,400.` The engine FAILs that claim on the arithmetic validator with evidence `{ qty: 3, price: 2800, stated: 9400, expected: 8400 }`, the gate records reason `[R1] arithmetic: ...`, the report's overall verdict is FAIL, and `verifyProofReport` returns true. A clean version of the same invoice (total corrected to $8,400) passes end to end with overall PASS.

### Bugs found and fixed during this phase

1. Sentence-final numbers: capture groups absorbed the closing period (`$8,400.`), so `parseNumber` rejected them and line totals, percent-of, and all money cross-references silently skipped. Fixed in `parseNumber` by stripping one trailing sentence period after cleaning.
2. Unit conversion pattern: no whitespace was allowed between the `=` separator and the converted value, so `10 km = 6.21 miles` never matched. Fixed by adding `\s*` after the separator group in `CONVERSION_RE`.
Both fixes are covered by the tests that originally exposed them.

## 2026-11-20 — Phase 2: web UI (three screens) + Firebase AI Logic adapter

Built to BRAND_NOTES.md and the Figma spec it summarises (Verification Blue #2457A6, Inter + Noto Sans SC, 240px sidebar, verdict colors kept separate from brand blue). All verdict data in the UI comes from the real core engine; nothing is hard-coded. The known mockup flaw (500 vs 120 jobs) is not replicated: the UI renders only live engine output, and the "Expected Output" panel shows the latest real run or explanatory placeholder text, never invented verdicts.

### What was built

- **Web app** (`index.html`, `web/main.ts`, `web/styles.css`, Vite + TypeScript, plain DOM, no UI kit):
  - Screen 1 — New Verification: source-type segmented control (AI Answer / Quote / Invoice / Announcement, Invoice preselected), paste area with live claim-extraction count from the real `splitClaims`, Clear / Load sample (loads the per-type sample from `src/samples.ts`; the Invoice sample is the canonical one with the planted arithmetic error), Verify button, 5-step Verification Pipeline panel that advances while the engine runs, Runtime Indicators, and an Expected Output panel fed by the latest real report.
  - Screen 2 — Proof Report: report header (derived title, source type, created time, processing mode derived from the model outputs actually recorded, seal status from `verifyProofReport`), three verdict summary cards (PASS / NEEDS REVIEW / FAIL counts from `report.summary`), per-claim cards with verdict chip, Evidence box (gate reasons plus the recorded model pass with source and model id), and the deterministic checks list (Arithmetic / Dates / Units / Citations / Numbers) with per-check status chips and recomputed evidence on fail/warn. Export JSON downloads the sealed report; Replay re-runs `runProofGate` on the stored input and shows the claim-by-claim comparison inline.
  - Screen 3 — History & Replay: reports persist in localStorage via the tested helpers in `src/history.ts`; stats (reports last 30 days, replays run, reports passed) computed from real entries; search plus verdict / source-type / date filters; per-row View (opens the report), Replay (re-runs, compares, and records replay count + match result on the entry), and Delete.
  - Header uses `brand/logo-lockup.png` (copied to `public/`), favicon is `brand/logo-icon.png`.
- **Firebase AI Logic adapter** (`src/firebaseAi.ts`): real code path on the Firebase JS SDK 13.4.0 (`firebase/app` + `firebase/ai`), written against the installed SDK's actual typings. Standard claims use a hybrid model with `InferenceMode.PREFER_ON_DEVICE` and `inCloudParams` cloud fallback; the response's `inferenceSource` decides whether the recorded `ModelOutput.source` is `on-device` or `cloud`. Escalated claims (per the existing deterministic `decideRoutingTier`, with the warn flag recomputed from the per-claim validators) use `InferenceMode.ONLY_IN_CLOUD`. If the on-device pass throws, the claim escalates to cloud and the escalation is written into the rationale (SPEC Section 4, trigger 4). Model replies are parsed as structured JSON and validated (`parseModelResponse`); malformed output becomes `uncertain` with the failure recorded, never silently trusted.
- **Config + honest demo mode** (`src/firebase-config.ts`): `firebaseConfig` is `null` by default; no project, key, or connection is invented anywhere. `createModelAdapter()` returns the Firebase adapter only when a complete config is present and initialises; otherwise it returns `MockModelAdapter`, and the UI labels that state in the top bar, a banner, the Runtime Indicators, and every report's processing mode ("Demo mode (mock model)", derived by `processingModeLabel` from the recorded outputs).
- **Browser-compatible sealing** (`src/sha256.ts`): `report.ts` no longer imports `node:crypto` (which does not exist in browsers). The pure TypeScript SHA-256 is byte-identical: after rebuilding, `node make-sample.mjs` reproduced `sample-proof-report.json` with the unchanged contentHash `db5ccba427cb053320569cffd957c0c537fa6292978381c486d0bb1a21959748` (git diff on the file: none), and the new tests cross-check the implementation against `node:crypto` and the FIPS known-answer vectors.
- **Samples** (`src/samples.ts`): one sample per source type; the invoice sample is the canonical test case (3 units at $2,800 = $9,400, recomputed 8,400, must FAIL).
- **History logic** (`src/history.ts`): storage-agnostic localStorage helpers (load / add with dedupe by content hash / update / remove, corrupt-data tolerant), `filterHistory`, `historyStats`, `compareReplay`, `deriveReportTitle`, `processingModeLabel` — all pure and unit-tested.
- `package.json`: added `firebase` (^13.4.0) dependency, `vite` (^5.4.21) devDependency, and scripts `dev`, `build:web`, `preview`. `.gitignore` now also ignores `dist-web/`. Note: the first backgrounded `npm install` in this session silently lost its package.json writes (empty package dirs, deps pruned by the next install); the install was redone in the foreground and verified in package.json before proceeding.

### Live smoke test — BLOCKED, all calls timed out (no HTTP response ever received)

`scripts/live-smoke.mjs` (new, not in the shipped bundle, not run by `npm test`) exercises the repo's own `FirebaseAiAdapter` from the dist build, plus one direct SDK call per path to capture raw response text, max 2 attempts per path. - PREFER_ON_DEVICE path (claim "Design services: 3 units at $2,800 = $9,400.", routed on-device): adapter attempts 1–2 and raw SDK attempts 1–2 all failed — adapter: `name: AbortError | message: Timeout has expired. | code: 20`; raw SDK: `generateContent timed out after 60000ms` (the script's own 60s race).
- ONLY_IN_CLOUD path (guarantee claim, routed cloud): identical failures, same verbatim errors.
- End-to-end `runProofGate(INVOICE_SAMPLE, { adapter })` therefore also failed: `name: AbortError | message: Timeout has expired. | code: 20`. No verdicts or processing-mode label could be produced with the live adapter.

What this does and does not show: no HTTP-level error was ever returned — nothing about App Check, API key restrictions, or quota. The failure is at request-completion level (the SDK's internal abort/timeout), and the run window overlapped a sandbox service restart. Post-run probes from the same machine reached `firebaselogic.googleapis.com` and `generativelanguage.googleapis.com` (bare GET → HTTP 404 at root, as expected) and `www.google.com` (200), so egress was up after the run; whether the timeouts were a transient egress interruption during the window or an SDK-in-Node hang is **not** determined. A re-run of `node scripts/live-smoke.mjs` in a fresh session is the next step to distinguish; it was not re-run beyond the 2-attempts-per-path limit.
